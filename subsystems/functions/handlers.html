Handlers

A Handler is the serving side of a function. It registers an implementation under a FunctionId, advertises that id in the node’s signed discovery entry, and answers calls that arrive over the /mosaik/functions/1.0 ALPN.

Handlers are created through a builder obtained from network.functions().handler(). The builder is terminated by one of two registration methods — serve for a closure, serve_fn for a Function implementation — both of which return Result<Handler<Req, Res, E>, BuilderError>.

Registering a closure

serve takes an async closure and infers the request, response and error types from it. Any Datum works for all three:

let handler = network
    .functions()
    .handler()
    .serve(|req: AddRequest, ctx| async move {
        req.a.checked_add(req.b)
            .map(|sum| AddResponse { sum })
            .ok_or(MathError::Overflow)
    })?;

Because a closure has no stable type name that both sides of the network could agree on, the base function id for a closure registration is derived from the request and response type names only. A caller built with caller::<AddRequest, AddResponse, MathError>() derives the same id and finds this handler without any shared constant.

The Function trait

When the function carries state or needs startup work, implement Function instead. The closure API is an adapter over this trait, so the two are interchangeable on the wire:

pub trait Function: Send + Sync + 'static {
    type Req: Datum;
    type Res: Datum;
    type Err: Datum;

    fn call(&self, req: Self::Req, ctx: CallContext)
        -> impl Future<Output = Result<Self::Res, Self::Err>> + Send;

    fn signature() -> UniqueId { /* type-name derived */ }
}

Initialization is deliberately outside the trait. Do any async warmup while constructing the instance, then register the ready value — a function that is not yet registered is simply not yet discoverable, so there is no window in which the network can route a call to a half-initialized handler:

struct Pricer { book: OrderBook }

impl Function for Pricer {
    type Req = QuoteRequest;
    type Res = QuoteResponse;
    type Err = QuoteError;

    async fn call(&self, req: QuoteRequest, _ctx: CallContext)
        -> Result<QuoteResponse, QuoteError>
    {
        self.book.quote(&req)
    }
}

let pricer = Pricer::load(order_book_source).await?;   // warmup
let handler = network.functions().handler().serve_fn(pricer)?;

The default signature() hashes the implementing type’s name together with the request and response type names. Callers reach the same id with network.functions().caller_for::<Pricer>(), so the Function type itself is the shared contract. Override signature() to pin a stable id independent of the Rust type name:

fn signature() -> UniqueId {
    unique_id!("pricing.quote")
}

CallContext

Every invocation receives a CallContext alongside the request. It carries the authenticated identity of the remote caller as recorded in the local discovery catalog at the time of the call:

.serve(|req: Req, ctx: CallContext| async move {
    let caller: &PeerEntry = ctx.caller();
    tracing::info!(caller = %caller.id(), tags = ?caller.tags(), "serving call");
    Ok::<_, ()>(handle(req))
})

The peer id is authenticated by the QUIC handshake, not self-reported, and callers that are absent from the local catalog are rejected before the function ever runs. into_caller() consumes the context and returns the owned PeerEntry.

One handler per function id

A node can serve a given effective wire id exactly once. Registering a second handler for the same id fails with BuilderError::AlreadyExists:

let first = network.functions().handler().serve(handle_a)?;
let second = network.functions().handler().serve(handle_a);
assert!(matches!(second, Err(BuilderError::AlreadyExists)));

Unlike a stream producer, the existing registration is not returned — it is bound to the closure or Function instance it was created with, so handing it back would silently give you someone else’s implementation.

Lifetime and shutdown

The Handler exclusively owns its registration. Dropping it:

  1. cancels in-flight dispatches for that function,
  2. removes the function id from the local discovery entry, and
  3. deregisters it so subsequent calls are rejected with FunctionNotFound.

A call whose dispatch is cancelled mid-flight by a drop is reported to the caller as FunctionNotFound — from the caller’s point of view the function is no longer served, which is exactly true — and the caller fails over to another handler if one is eligible.

Keep the handle alive for as long as you want to serve. Binding it to _ drops it immediately; bind to a named variable (or _handler) instead.

Concurrency

with_max_concurrent(n) bounds how many calls may execute at once. Calls arriving while the bound is saturated are rejected with a NoCapacity close reason rather than queued, which lets the caller fail over to a handler that has capacity instead of waiting behind a full queue:

let handler = network.functions().handler()
    .with_max_concurrent(32)
    .serve(|req: Req, _| async move { Ok::<_, ()>(handle(req).await) })?;

The default is unlimited. Choosing a bound turns overload into an explicit, observable rejection and is what makes horizontal scaling across handler nodes work.

Rejections

Before the function runs, the acceptor screens every call. Each screen has a distinct close reason so the caller can distinguish “try someone else” from “this call is malformed”:

Close reasonCodeCause
UnknownPeer401Caller is not in this node’s discovery catalog
DifferentNetwork101Caller’s NetworkId does not match
FunctionNotFound11_404No handler registered for the requested id
NotAllowed11_403require predicate or caller ticket validation failed
NoCapacity11_509max_concurrent is saturated
ProtocolViolation400Request payload did not decode into Req
HandlerFailure11_500Reply could not be encoded — a handler-side fault

UnknownPeer is self-healing rather than terminal: the caller responds by forcing a catalog exchange with this handler and retrying once, so a handler that has not yet learned a new caller does not permanently reject it. See Callers.

Application errors are not failures

A function returning Err(Self::Err) is a successful protocol exchange. The typed error travels back to the caller as CallError::Application(E) and never triggers failover — the function ran, and its answer stands. Retrying it on another handler would at best waste a round trip and at worst duplicate a side effect.

Reserve close reasons for conditions where a different handler might legitimately produce a different outcome, and the typed error type for everything the function itself decides.

Statistics

Each handler tracks its own counters:

let stats = handler.stats();
stats.served();    // calls that completed with a reply, app errors included
stats.failed();    // handler-side faults: bad request, encode failure, shutdown
stats.inflight();  // calls currently executing

These are process-local. For fleet-wide observability the subsystem also emits mosaik.functions.* metrics — see Metrics & Observability.
